# Жизненный цикл ML-модели: эксплуатация, мониторинг, переобучение

Диаграммы для сервиса подбора посёлка (`video_app_a_production`).
Модель: классификатор посёлка (`global_best_model.joblib`, xgboost),
инференс — в Yandex Serverless Container. Ролик фиксированный по посёлку
(вариант A), переобучение — по процессу из `Model_retrain_BPMN.md`.

> **Принцип процесса:** переобучение выполняется **автоматическим
> пайплайном с контролем** (данные → обучение → проверка порогов →
> канареечный деплой). Человек вмешивается только при **больших отклонениях**
> (fail контрольных ворот). Исключение: при появлении **нового класса**
> (нового посёлка) — обязательно **ручная верификация** всего процесса.

**Ключевые SLA эксплуатации:** холодный старт (загрузка модели) измеряется в

живость + наличие модели.

## 3. Триггеры переобучения

| Триггер | Пример для этого проекта |
|---|---|
| **Новый класс (новый объект недвижимости)** | Открылась продажа в новом посёлке — модель не может предсказать класс, которого не было в обучении; требуется переобучение с новым CLASS_MAP |
| Дрейф данных (новый вид данных) | Появились новые значения анкеты / категории фич |
| Дрейф данных (по времени) | Прошло более 6 месяцев с последнего обучения |
| Запрос от бизнеса | Маркетинг изменил приоритетные сегменты покупателей |
| Накоплено много новых данных | Достаточно новых размеченных лидов (см. порог ниже) |
| Плановое переобучение | Регулярный квартальный цикл |

Порог данных для переобучения: как минимум столько же свежих примеров,
сколько в текущем трейне, ИЛИ ≥ 30% объёма трейна, если модель начала
проседать по accuracy. Переобучение только на «старых» данных запрещено.

## 4. Диаграмма переобучения (полный контур с отказами)

> Схема ниже описывает полный контур с отказами. В штатном режиме шаги
> «согласование» и «отказ» почти не задействуются: пайплайн проходит
> ворота автоматически; человек подключается только по отметке
> «большие отклонения» или в режиме нового класса (ручная верификация).

```mermaid
flowchart TB
    T(["Триггер сработал"]) --> D1{"Проверка пригодности
    новых данных"}
    D1 -- "пустые/битые данные,
    соединение недоступно" --> DK["Сбор данных отклонён:
    причина фиксируется для аудита"]
    DK --> T
    D1 -- ок --> D2["Датасет заморожен и
    версионируется"]
    D2 --> R1["Обучение кандидата №1"]
    R1 --> CMP{"Кандидат лучше
    текущей модели по
    accuracy и latency?"}
    CMP -- нет --> CNT["Счётчик попыток +1"]
    CNT -- "попытки < 3" --> R1
    CNT -- "≥ 3 неудач" --> FAIL["Фиксация результатов
    в журнале экспериментов,
    переобучение закрыто"]
    FAIL --> T
    CMP -- да --> R12["Шаг R12: согласование
    с владельцем бизнеса"]
    R12 --> VET{"Согласие выдано?"}
    VET -- нет --> REJ["ОТКАЗ остаётся в истории
    для аудита (кто, когда,
    почему), повторный триггер
    должен аргументировать
    новыми данными"]
    VET -- да --> DEP["Контроль деплоя:
    прогрев, стратегия
    постепенной нагрузки"]
    DEP --> T1["5%"] --> T5["25%"] --> T10["50%"] --> T11["100%"]
    T11 --> MON["Мониторинг (см. схему 2):
    тест стабильности 7 дней"]
    MON --> FIN["Новая модель в production.
    Предыдущая хранится до
    следующего успешного цикла"]
```

Правила контура:

1. **Отказ всегда письменный и остаётся в аудит-журнале.** Окончательное
   решение о замене модели принимает владелец бизнеса (техкоманда только
   рекомендует).
2. **Счётчик попыток обучения** фиксируется; более 3 неудачных кандидатов
   закрывают цикл до нового триггера.
3. **Контроль деплоя** — постепенный перевод трафика (канареечный), с
   мгновенной возможностью rollback.
4. **Карантин 7 дней** — модель считается «прошедшей» только если accuracy и
   технические метрики стабильны весь срок.
5. Данные для обучения проходят **валидацию пригодности**: проверка на
   пустые значения, количество строк, работу соединения и шлюза (S3/AI-вызовы).
   Непригодные данные → отказ с фиксацией причины для аудита.

## 5. Роли в процессе

| Роль | Зона ответственности |
|---|---|
| ML-инженер | обучение, оценка метрик, деплой, мониторинг |
| Владелец бизнеса | согласование замены модели, финальное решение |
| Аудитор / журнал | сохранение отказов, версий датасетов, моделей и причин |
